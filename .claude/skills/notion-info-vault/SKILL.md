# 记进库里 (Notion 信息与灵感库归档)

## 定位

这是整个系统中的**捕获**环节：低摩擦、不做状态判断。所有判断（这条值不值得跟进、归档还是放弃、是否新建主题、调整假设）留给复盘（periodic-review 技能），这里不做。

**核心规则：「一句话小结」必须是用户的原话。** 理由：谁先写总结，谁就框定了复盘时的第一印象。哪怕用户的话很简陋，也比直接看 AI 的输出更能促进思考。为了不增加摩擦，由 Claude 在入库时主动询问，而不是让用户事后去 Notion 里打字。

## 触发条件

用户说出以下类似表达时触发：
- "记进库里"
- "存进信息库/灵感库"
- "归档这次讨论/这段对话"
- "把刚才的想法记下来"（在明确指向这个 Notion 数据库的语境下）
- "这是XX那条的后续，记进库里"（带衍生关系的捕获）
- 用户接受了 Claude "要不要记进库里"的提议

如果用户只是笼统地说"记一下"而没有明确指向这个数据库，先确认是否要存入「信息与灵感库」，而不是默认写入。

## 目标数据库

- 数据库名称：信息与灵感库
- data_source_id: `collection://3e627141-a910-80f6-b4de-000b0e86ddc4`
- 关联库：计划与关注 `collection://d64bfa5d-3677-4546-83b4-80c81a00c727`（本库的"相关计划"字段关联到它）
- 用 Notion 的 fetch 工具重新确认 schema（字段名称、可选值）是否有变化，若字段已被用户改名或增删，以当前实际 schema 为准，不要假设本文件里的字段永远不变。

## 小结对话（写入前必须完成）

1. **先问，不先给。** 识别出要归档的内容后，先请用户用一两句话说出他从这段内容里得到的结论。问法简短，例如："用一两句话说说你从这段讨论里带走的结论？怎么粗糙都行。"
   - 提问时**不要**先给出 Claude 自己的总结、要点清单或候选答案，避免框定用户的思路。
   - 内容很长、用户可能需要提示时，最多提一句讨论涉及的范围（如"从器官比喻聊到了认知外包和审美"），不给结论。
2. **回应。** 用户给出原话后，Claude 做简短回应，2-3 点即可：
   - 补充：用户的话漏掉的、讨论中重要的点
   - 反驳：用户的话里站不住、过度概括或与讨论内容有出入的地方
   - 用户的话已经很到位时直说，不要为了回应而硬凑。
   然后问一句是否要调整，并顺带请用户确认 Claude 草拟的"下一步"（一句话，不单独再开一轮）。用户可以改，也可以说"就这样"。
3. **定稿。** 「一句话小结」写入用户**最终确认的原话**，逐字照录：不润色、不改写、不合并、除标点外不补任何内容。用户说"把你说的第二点加进去"时，请他用自己的话说出来，或照录他明确认可的组合方式。
4. **用户不想写时。** 用户说"你写吧""没想好""跳过"：「一句话小结」留空，不用 Claude 的版本代替；在回复中说明小结留空，复盘时再补。
5. **无人值守时**（定时任务、用户不在场）：小结留空，照常写入其他字段。

## 字段与写入规则

- **标题**（title）：由 Claude 独立拟定，概括这段讨论/信息的主题，8-20字左右，方便在列表里识别。标题和小结分工不同：标题说“这条是关于什么的”，小结说“用户的结论是什么”。不要照搬或压缩用户的小结来当标题，不要用"讨论""聊天"这种空泛词。
- **类型**（select: 信息流 / 灵感 / 决策）：
  - 来自用户订阅的媒体/信息流条目 → 信息流
  - 用户与AI讨论中产生的想法、结论、方法论 → 灵感
  - 决策类字段（动作、标的、回看日、判定）按库中现有约定处理
- **来源**（text）：具体来源，例如"与Claude的讨论"、媒体名、卖方名等。
- **主题标签**（multi_select）：从现有选项中选最贴合的1-2个；都不合适时可新增（用 update_data_source 的 ALTER COLUMN ... SET MULTI_SELECT，并列出全部原有选项避免覆盖丢失）。两个库的主题标签应保持一致：给信息库新增选项时，同样补到计划库的"主题标签"里。不要滥用"待归类"。
- **状态**（select）：新建记录**一律为"待处理"**，不论讨论看起来多完整。含义与流转：
  - 待处理：还没在复盘中被用户看过（捕获时唯一使用的值）
  - 跟进中：用户在复盘中判断值得投入，有未完成的下一步
  - 已归档：下一步已完成，或已转化为衍生记录/计划项，这条本身收尾
  - 已放弃：不值得跟进
  后三种只在复盘时由用户决定，捕获时不设置。更新已有页面时也不要改动其状态。
- **一句话小结**（text）：**用户原话**，见上方"小结对话"。这是全库最重要的字段，也是复盘时唯一先看的内容。
- **下一步**（text）：由 Claude 草拟，在小结对话里请用户一并确认。有明确后续行动写一句；需要观察写"继续观察"；确实不需要跟进写"无"。空着和"无"含义不同，复盘时需要区分。这个字段记录的是入库时的意图，事后不要覆盖；后续动作的完成情况由衍生关系体现。
- **链接**（url，可选）：有可引用原文链接则填，AI对话本身没有可分享链接时留空。
- **相关计划**（relation，可选）：见"与计划库的衔接"。可以关联追踪主题，也可以关联具体的日程事件。
- **衍生自**（relation，可选）：见"衍生关系"。对侧"衍生出"自动反向显示，不要手动填写。

页面正文（content）用 Notion Markdown，用户的话与 Claude 的整理明确分开：

```
## 我的结论（原话）
> （用户最终确认的原话；若留空则写"待复盘时补"）

## 背景
（触发这次讨论/这条信息的情境；如果是某条记录的后续，说明是哪条记录的哪个下一步）

## 讨论要点（Claude 整理）
（分点列出讨论中的关键内容，2-5条）

## Claude 的补充与反驳
（小结对话中 Claude 的回应，以及用户是否采纳；用户未写小结时省略此节）

## 落地方案（如适用）
（具体怎么做）
```

## 衍生关系

当新记录是某条已有记录"下一步"的产出（读完了报告、查了数据、展开了想法、冒出了新方向）时，在新记录的"衍生自"里关联那条源记录。

1. **用户明说了**（"这是XX那条的后续"）→ 找到对应记录，直接关联。找到多条候选时，列出来让用户选。
2. **用户没说，但匹配明确**：查询状态为"跟进中"（以及近期"待处理"）的记录，如果新内容正好对应某条记录的"下一步"，关联它，并在回复中说明挂到了哪条，方便用户纠正。
3. **可能相关但不确定** → 不关联，只在回复中提一句"可能是XX那条的后续，复盘时确认"。
4. **发散**：一条源记录引出的多个分支，都挂回同一个源头；只有当某个分支本身又引出新的后续时，才从这个分支继续往下挂。不要为了串联而把平行分支连成链。
5. 不要因为挂上了衍生关系就修改源记录的状态——源记录是否收尾，由用户在复盘时决定。

## 与计划库的衔接

捕获时只做轻量衔接，不替用户做判断。先查询计划库中 类型=追踪主题且状态=进行中 的条目，以及 类型=日程事件且状态=待发生 的条目。

1. **关联主题**：如果用户明确提到这条记录属于某个主题，或内容与某个进行中主题的匹配毫无歧义，就在"相关计划"字段里关联该主题页面（值为页面URL的JSON数组）。只是可能相关、不确定时，不要关联，在回复中提一句"可能和X主题有关，复盘时确认"。
2. **这条记录是某个事件的结果**：如果内容是计划库里某个"待发生"事件的实际结果，在"相关计划"里关联该事件，并在回复末尾问一句是否顺便补这个事件的结果。用户同意后按 plan-event-tracker"补结果"的规则处理，不要在没问的情况下直接改事件。
3. **这条记录提到了未来的新事件**：如果内容里有一个与进行中主题相关、但计划库里还没有的日程事件（不论多远——每个事件都有自己的提醒），在回复末尾问一句是否要加进计划库（由 plan-event-tracker 处理），不要自行添加。
4. **改期或取消**：如果内容表明某个待发生事件改期或取消，提醒用户并问是否同步更新（由 plan-event-tracker 处理，会同时调整提醒）。
5. **不要**在捕获时新建追踪主题、修改假设或改变计划库里任何条目的状态——这些属于复盘或 plan-event-tracker 的范围。多个衔接问题同时出现时，在回复末尾合并成一个简短的问题。

## 执行步骤

1. 识别触发语，确认要归档的是当前对话中的哪一段内容（通常是最近几轮）。
2. **进行小结对话**：先问用户原话 → 回应补充/反驳 → 用户定稿（顺带确认"下一步"）。这一步在任何 Notion 写入之前完成。
3. 按上述规则整理其余字段和正文内容，状态设为"待处理"。
4. 如果需要新增主题标签选项，先用 notion-update-data-source 更新 schema（保留所有原有选项），并同步到计划库。
5. 按"衍生关系"判断是否填写"衍生自"。
6. 按"与计划库的衔接"判断是否填写"相关计划"，并记下需要问用户的衔接问题。
7. 用 notion-create-pages 写入页面，parent 用 `{"data_source_id": "3e627141-a910-80f6-b4de-000b0e86ddc4", "type": "data_source_id"}`。关联字段的值为页面URL的JSON数组。
8. 写入完成后，用简短的一段话（不是逐字段罗列）告诉用户已经记录了什么、挂了哪些关联（如有）、小结是否留空，给出页面链接；有衔接问题的，在末尾问。不要在回复里重复整个正文内容。

## 注意事项

- 任何情况下都不要用 Claude 写的句子填「一句话小结」，包括"帮用户润色"。
- 如果这次讨论内容混合了"信息流"和"灵感"两种性质，选择占主导的那一种作为类型，另一种可以在正文里提及。
- 如果用户之前在同一对话里已经归档过一次，且这次只是追加/修正，优先考虑更新已有页面而不是重复创建（用 fetch 找到该页面URL，再用 update_page 类工具修改），除非用户明确要新建一条记录。若用户想修改已有记录的小结，同样走小结对话，以用户新的原话替换。区分"修正同一条"和"产出了后续"：后者应新建记录并挂衍生关系。
