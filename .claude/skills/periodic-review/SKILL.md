# 复盘（不限定周期）

## 定位

复盘是系统中做**判断**的环节：平时只捕获，平时只盯事件，所有判断集中在这里——包括信息库每条记录的去留、决策的回看，以及计划层面的决定。
分工：整理、聚类、汇总由Claude完成；取舍判断必须由用户做出。Claude不替用户新建、调整、结案或放弃追踪主题，不替用户判定决策，也不替用户改信息库记录的状态。

复盘没有固定周期。它可能由定时任务（例如每周一次）触发提醒，也可能由用户在任何时候手动触发；两次复盘之间可能隔几天，也可能隔几周。

## 数据库

- 信息与灵感库：`collection://3e627141-a910-80f6-b4de-000b0e86ddc4`（字段含 标题、类型（信息流/灵感/决策）、来源、主题标签、状态、一句话小结、下一步、相关计划、衍生自、衍生出、标的、动作、回看日、判定（理由成立/部分成立/理由不成立）、Created time、Last updated time）
- 计划与关注：`collection://d64bfa5d-3677-4546-83b4-80c81a00c727`（字段含 名称、类型（追踪主题/日程事件/复盘）、日期、状态、判定（证实/部分成立/推翻）、主题标签、假设、证实信号、推翻信号、预期、结果、所属主题、检验事件、相关记录）
- 开始前用 fetch 确认两个库的当前 schema，以实际为准。

## 信息库的状态含义

- **待处理**：捕获时的默认值，表示用户还没在复盘中看过。复盘时要做**分拣**。
- **跟进中**：用户判断值得投入、有未完成的下一步（读报告、查数据、展开想法等）。复盘时要**查兑现**。决策类的"跟进中"表示等待回看。
- **已归档**：下一步已完成，或已转化为衍生记录/计划项；决策类表示已回看并判定。
- **已放弃**：不值得跟进。

后续动作的完成情况由"衍生出"（产出了新记录）和"相关计划"（转为主题或事件）体现，不靠状态本身。

## 决策的生命周期

决策记录（类型=决策）走一条独立的路径：
1. **待处理** → 复盘分拣时，决策默认转为**跟进中**（等待回看）。同时确认回看日合理；如果理由没记录，这是最后一次让用户补记的机会（注明"事后补记"）。
2. **跟进中** → 回看日到期后，在复盘里做**决策回看**。
3. 回看完成 → **已归档**，"判定"填理由成立 / 部分成立 / 理由不成立。或者用户决定延长观察 → 更新回看日，保持跟进中。

**判定看理由，不看盈亏**。赚了钱但当初的理由没应验（运气），是"理由不成立"；亏了钱但理由应验了、只是被其他因素盖过，可以是"理由成立"或"部分成立"。盈亏和市场表现写在正文的回看段落里。这样分开记，累积下来才能区分"判断力"和"运气"。

## 追踪主题的生命周期

- **进行中**：正在跟踪。"日期"字段是下次复查日。
- **已完成（结案）**：关键检验点已过、假设已有定论。必须填"判定"（证实/部分成立/推翻），并在"结果"字段写一句结案复盘。
- **已放弃**：不再值得跟踪（没有定论就失去兴趣或失去相关性）。"判定"留空。

区分结案和放弃：有定论就是结案，哪怕定论是"推翻"。不要把被推翻的主题记成放弃——那会抹掉最有校准价值的数据。

## 复盘记录（用于确定"上次复盘"）

每次复盘完成后，在计划库里写入一条 类型=复盘 的记录：
- 名称：`复盘 YYYY-MM-DD`
- 日期：复盘当天；状态：已完成
- 正文：本次覆盖的区间、用户对三个问题的回答要点、所做的变更清单

如果"类型"字段还没有"复盘"选项，先用 notion-update-data-source 补上（ALTER COLUMN "类型" SET SELECT(...)，必须把"追踪主题""日程事件"等原有选项一并列出）。用户如果在阶段二前离开、没有做任何判断，不写复盘记录（本次不算完成一次复盘）。

## 确定复盘区间

按以下优先级确定回看区间的起点：
1. 用户明确指定（"回顾过去一个月""从9月1日起"）→ 用用户的。
2. 否则用最近一条 类型=复盘 记录的**创建时间**（Created time，精确到时刻，避免同一天内复盘前后的记录被重复计入）。
3. 都没有（首次复盘）→ 默认过去7天，并告诉用户。

前瞻区间（看即将发生的事件）默认未来7天；用户说明下次复盘大概什么时候时，延长到那个时间点。每个事件都有自己的写预期提醒，所以前瞻区间只是让用户心里有数，不必过长。

在摘要开头用一行注明区间，例如"本次覆盖 9月18日–9月27日（自上次复盘起）"。

跳过复盘不补做：区间长就是区间长，按下面的"长区间处理"压缩，而不是分几次逐周补。

## 阶段一：生成复盘摘要（Claude完成）

### 取数

1. 信息库：
 - 所有状态为"待处理"的记录（不论创建时间）
 - 所有状态为"跟进中"的非决策记录，连同它们的"衍生出"和"相关计划"
 - 所有类型=决策、状态=跟进中、回看日已到期或落在前瞻区间内的记录
 - 区间内新建的记录（用于主题信号聚类）
 - 正文含"类型存疑"的记录
 - 所有已判定的决策（用于决策命中率）
2. 计划库：
 - 状态=进行中的追踪主题，连同它们的检验事件
 - **所有日期已过、状态仍为"待发生"的日程事件（不受区间限制）**——这些是漏补结果的，包括补结果提醒响了但用户没回复的
 - 区间内已完成的日程事件（回看）
 - 前瞻区间内的日程事件
 - "日期"（复查日）已到期或落在前瞻区间内的追踪主题
 - 最近两条 类型=复盘 的记录（用于判断"跟进中"是否停滞）
 - 所有已结案（状态=已完成）的追踪主题及其判定（用于命中率）

### 摘要结构（简短，控制在一屏左右）

1. **主题信号**：按主题标签和"下一步"内容聚类，指出区间内反复出现的方向（附条数），以及同一主题下观点矛盾或方向变化的条目。把分散在多条记录里、指向同一假设的"下一步"归并在一起。已有进行中主题的，标明哪些新记录可能与之相关。区间内如有新决策，指出它们和哪些主题、哪些信息对应。
2. **待处理分拣**：逐条（或按主题分组）列出待处理记录的标题和一句话小结，并给出建议去向：跟进中 / 归档 / 放弃 / 挂到某主题。决策类默认建议"跟进中"，并列出回看日请用户确认；缺理由的决策要标出。建议只是建议，由用户决定。超过14天仍为待处理的，单独标出。
3. **跟进中兑现检查**（非决策类）：对每条跟进中记录说明：
 - 有新的衍生记录或关联计划 → 列出产出，提示"是否可以收尾归档"。
 - 没有任何产出 → 问是否做了；如果它的 Last updated time 早于上上次复盘记录的创建时间，且此后没有新衍生，标为"停滞"，建议降级为归档或放弃。注意：复盘时在正文里追加说明也会更新 Last updated time，所以如果最近的编辑只是复盘补充、没有实际进展，也应视为停滞。
 - 检查衍生关系是否有遗漏：区间内新记录中，内容明显对应某条跟进中记录的"下一步"但没挂"衍生自"的，列出来请用户确认。
4. **决策回看**：对每条回看日已到期的决策：
 - 列出当时的动作、理由、预期、认错条件（原样引用，不要转述成事后的语言）。
 - 用网络搜索核实标的自决策日以来的表现和关键变化（附来源），以及理由里提到的因素是否应验。
 - 给出建议判定（理由成立/部分成立/理由不成立），并明确区分"理由是否应验"和"盈亏如何"。判定由用户确认。
 - 前瞻区间内即将到期的决策，只列标题和回看日。
5. **事件回看**：
 - **漏补结果**：所有日期已过仍为"待发生"的事件，排在最前。可以先搜索实际结果附上，让用户确认即可。
 - 区间内已完成事件的预期 vs 结果；指出触及某主题证实/推翻信号的结果。
6. **即将发生的事件**：列出前瞻区间内的事件及所属主题，标出哪些还没写预期。
7. **需复查的主题**：复查日到期的主题，附上自上次复查以来的相关记录数（为0的提示可能该放弃）。如果某主题的检验事件已全部完成，或关键检验点（如到期日）已过，提示"是否可以结案"，并根据事件结果和信号给出建议判定供用户参考。
8. **类型存疑**（有才展示）：汇总正文标了"类型存疑"的记录。同一种情况累计出现2–3次，建议新增类型，并说明它在复盘时的处理方式和现有类型有何不同；处理方式没有不同的，建议归入现有类型并去掉存疑标记。
9. **判断记录**（有已结案主题或已判定决策时才展示，一两行即可）：主题累计结案X个（证实A / 部分B / 推翻C）；决策累计判定Y个（理由成立D / 部分E / 不成立F）。如果某类标签、某类动作（如买入 vs 卖出）下明显更准或更不准，点一句。

摘要末尾固定提三个问题：
1. 这段时间什么东西反复出现，值得作为主题追踪吗？
2. 有什么信息改变了你原来的看法？
3. 接下来你要带着什么问题去看信息流？

### 长区间处理（超过约21天）

- 主题信号不逐条列出记录，只报主题层面的聚类和数量，每个主题最多点2条最关键的记录。
- 增加一项"趋势变化"：同一主题在区间前半段和后半段的热度或观点有何不同。
- 待处理分拣按主题分组给出"整组归档/整组放弃"选项，减少用户逐条确认的负担（决策类除外，决策始终单独列出）。

### 交付方式

- **用户手动触发**：直接在对话中给出摘要，等待回答。
- **定时任务触发**：这是一次复盘**提醒**。用 SendUserMessage 发出摘要（开头一句话说明这是定期复盘提醒、覆盖区间），然后停在阶段一。**不要**代替用户回答、不要改任何记录的状态、不要更新计划库、不要写复盘记录。如果距上次复盘很近（例如用户前两天刚手动复盘过）且区间内几乎没有新内容，只发一句简短提醒、漏补结果的事件、到期的决策回看和即将发生的事件即可。

## 阶段二：根据用户判断更新（用户回答后）

用户通常用几句话回答。根据回答执行，只做用户明确表达的变更：

**信息库**
- **分拣待处理**：按用户意见改为 跟进中 / 已归档 / 已放弃。改为跟进中时，确认"下一步"写得足够具体（用户补充了内容就更新到正文，"下一步"字段保留原意图，必要时在正文追加一行带日期的补充）。决策转为跟进中时，按用户意见调整回看日；用户补记的理由注明"YYYY-MM-DD 事后补记"。
- **收尾跟进中**：用户确认下一步已完成或已转化 → 改为已归档；在正文追加一行带日期的"收尾说明"（产出是什么、衍生了哪些记录）。
- **降级停滞项**：按用户意见改为已归档或已放弃，正文注明日期和原因。
- **补衍生关系**：把用户确认的遗漏衍生关系挂上（在子记录的"衍生自"里填源记录）。
- **决策回看**：用户确认判定后，填"判定"，状态改为已归档；在正文追加 `## 回看（YYYY-MM-DD）` 段落：实际发生了什么、理由哪里应验哪里没有、盈亏表现（用户愿意说才写）、一句教训。不要改写当时的理由/预期/认错条件。用户决定延长观察 → 更新回看日，正文追加一行说明，保持跟进中。有后续操作的（如加仓、清仓），应作为新决策入库并挂"衍生自"。
- **类型调整**：用户同意新增类型时，用 ALTER COLUMN "类型" SET SELECT(...) 补上（保留原有选项），把相关记录改过去、去掉存疑标记，并提醒用户可能需要更新 notion-info-vault 和本技能的类型说明。用户不同意就去掉存疑标记。

**计划库：事件**
- **补漏掉的结果**：按 plan-event-tracker"补结果"的规则写入，状态改为已完成。
- **即将发生的新事件**：用户确认要关注的新事件，按 plan-event-tracker"加事件"的规则添加（核实日期、挂到主题、创建提醒）。

**计划库：主题**
- **新建追踪主题**：类型=追踪主题，状态=进行中；填写假设、证实信号、推翻信号（把用户的话整理成可检验的表述，有歧义时确认；用户只给了假设时，可以从假设推出信号，但要明确告诉用户是推出来的并请其确认）。"维持现状"类假设的推翻信号要包含向上和向下两个方向。设置复查日（默认两周后，或某个关键事件之后）；把区间内相关信息记录关联到"相关记录"。如有明确的检验事件，按 plan-event-tracker 添加。
- **调整主题**：更新假设/信号字段，在正文"变更记录"追加一行带日期的说明（保留历史，不覆盖原因）。假设被改写前的原文也要写进变更记录，否则结案时无法判断最初的判断对不对。
- **结案主题**：状态=已完成；"判定"填用户确认的证实/部分成立/推翻；"结果"字段写一句结案复盘（实际发生了什么、判断对在哪或错在哪）；正文追加带日期的结案说明。判定必须由用户确认，Claude可以给建议。结案时还有未发生的检验事件的，按下一条"名下事件处理"。如果有基于该主题、仍在跟进中的决策，提示用户是否一并回看。
- **放弃主题**：状态=已放弃，"判定"留空，正文注明日期和原因。然后处理名下事件。
- **名下事件处理**（结案或放弃时）：列出该主题下所有"待发生"的检验事件，逐个问用户：取消（按 plan-event-tracker"改期、取消、改挂"规则：状态改为已放弃、删除提醒）还是改挂到其他进行中的主题（更新"所属主题"，提醒保留）。用户一句话说"全部取消"也可以。
- **关联记录**：把用户确认相关的信息记录挂到对应主题。
- **复查日**：给本次复查过的进行中主题设置下一个复查日。

**收尾**
- **写复盘记录**：按"复盘记录"一节写入。

完成后用几行话总结变更（分拣了多少条、收尾/降级了哪些跟进项、回看了哪些决策、补了哪些事件结果，新建/调整/结案/放弃了哪些主题，取消了哪些事件，接下来要写预期的事件），不要逐字段罗列。

## 原则

- 追踪主题保持少量（建议同时进行中不超过3-5个）。超过时提醒用户取舍。
- "跟进中"（非决策类）也应保持少量。数量持续增长时提醒用户：跟进中是承诺投入的时间，不是第二个积压堆。决策类的跟进中只是等回看日，不受此限。
- 回看决策时保持中立：不要用事后的语言重写当时的理由，不要给出买卖建议。
- 用户只回答了部分问题也可以，按已有回答更新，其余保持不变。
- 最低版本：用户说"只有10分钟"时，只呈现漏补结果的事件、到期的决策回看、即将发生的事件、停滞的跟进项和第3个问题；这种情况下仍写复盘记录，并在正文注明是简版。待处理分拣留到下次。
