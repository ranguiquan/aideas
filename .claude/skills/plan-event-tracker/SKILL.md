# 日程事件的即时处理（计划与关注）

## 定位

计划库的更新原则上集中在复盘（periodic-review 技能；复盘时间不固定，可能是定时提醒，也可能是用户手动触发）。本技能只处理事件层面的"时间不等人"的动作：

1. **加事件**：得知一个与进行中主题相关的事件（平时即时添加，或复盘时按本技能规则添加）。
2. **写预期**：事件发生之前写下预期。这是唯一有硬截止时间的动作。
3. **补结果**：事件发生后记录结果（也可攒到复盘时补，但出乎意料的结果最好趁新鲜记）。
4. **改期、取消、改挂**：事件本身变化，或所属主题结案/放弃时处理名下事件。

为了不让"写预期"依赖复盘节奏，**每个事件都配两个一次性提醒**（写预期、补结果），见"5. 事件提醒"。

新建/调整/结案/放弃追踪主题**不在**本技能范围内，属于 periodic-review。

## 触发示例

- "把下周四的CPI加进计划" / "关注一下X号的FOMC"
- "记一下我对明天非农的预期" / "写个预期"
- "CPI出来了，补一下结果" / "这个事件结果是……"
- "XX改期了" / "XX取消了"
- 定时任务触发的"写预期提醒"或"补结果提醒"
- notion-info-vault 入库时发现内容是某事件的结果、用户同意顺便补结果
- periodic-review 结案或放弃主题时处理名下事件

## 目标数据库

- 计划与关注：`collection://d64bfa5d-3677-4546-83b4-80c81a00c727`
- 先用 fetch 确认当前 schema，以实际字段为准。关键字段：名称、类型（追踪主题/日程事件/复盘）、日期、状态（进行中/待发生/已完成/已放弃）、主题标签、预期、结果、判定（仅主题结案用，本技能不写）、所属主题（关联到本库的追踪主题，对侧为"检验事件"）、相关记录（关联信息与灵感库）。

## 1. 加事件

1. 确认事件的准确日期（和时间，如有）。用户说得模糊（"下周的CPI"）时，用网络搜索核实官方发布日程，不要凭记忆填日期。
2. 用户时区为新加坡（UTC+8）。有具体发布时间时，按新加坡时间填写带时间的日期，并在正文注明原始时区的时间。多日会议用日期区间。
3. 查询 类型=追踪主题、状态=进行中 的条目，把事件关联到对应主题（"所属主题"）。
 - 用户指明了主题或匹配无歧义 → 直接关联。
 - 找不到匹配主题 → 问用户：挂到哪个主题，还是先不挂、留到复盘时决定。**不要为了挂靠而新建主题。**
4. 写入：类型=日程事件，状态=待发生，主题标签与所属主题一致。正文写一句"检验点"（这个事件对主题意味着什么）和日期来源链接。其他字段可留空，不要为了完整而追问。
5. 按"5. 事件提醒"创建提醒，并把提醒记录到页面正文。
6. 如果事件在48小时内发生，不设写预期提醒，直接问用户是否现在写预期。

## 2. 写预期

1. 找到对应事件页面（按名称和日期查询）；不存在就先按"加事件"建立。
2. **先检查事件是否已经发生**。如果已经发生，不要把内容写进"预期"——事后写的预期会被结果污染，失去校准价值。改为写入"结果"，并在正文注明"事后记录，无事前预期"。
3. 预期应尽量具体可检验：预期的数值或方向 + 如果偏离会意味着什么（对所属主题的假设有什么影响）。用户表达模糊时，可以帮他整理成可检验的句子，但必须让用户确认，不要替用户编造判断。
4. 在正文或"预期"字段中标注写下预期的日期。

## 3. 补结果

1. 找到事件页面，写入"结果"：实际数据/结果 + 市场反应（用户提供或经搜索核实的）+ 对所属主题假设的含义（证实/推翻/无关）。
2. 核实实际数据时用网络搜索，并在正文附上来源链接。
3. 状态改为"已完成"。如果这是在补结果提醒之前手动完成的，补结果提醒仍会触发，但它会检测到已完成并只推送一句确认，所以不必删除。
4. 如果有对应的信息库记录（如用户刚记进库里的那条新闻），把它关联到事件的"相关记录"。
5. 如果结果明显触及所属主题的"证实信号"或"推翻信号"，在回复里提示用户，但**不要**修改主题本身——留到复盘时由用户决定。如果这是主题的最后一个或关键检验点，提醒用户下次复盘时考虑结案。

## 4. 改期、取消、改挂

- **改期**：更新页面日期，用 update_trigger 把两个提醒的 run_once_at 按新日期重算，并更新页面里的"提醒"一节；正文追加一行带日期的改期说明。新日期在48小时内的，删掉写预期提醒并当场问。
- **取消**：状态改为"已放弃"，正文注明日期和原因，用 delete_trigger 删掉还没触发的提醒，并把页面"提醒"一节标为"已删除"。
- **改挂**：所属主题结案或放弃、用户决定把事件移到另一个进行中主题时，更新"所属主题"和主题标签；提醒保留（提醒触发时会实时读取所属主题，不需要改 prompt）。
- **批量处理名下事件**（由 periodic-review 在结案/放弃主题时调用）：列出该主题下所有"待发生"的事件及其提醒时间，按用户逐个或整体的决定（取消/改挂）执行上述规则。处理完用一行话说明删除了哪些提醒。
- 从页面"提醒"一节读取 trigger ID；找不到时用 list_triggers 按名称查找。

## 5. 事件提醒

每个日程事件创建两个**一次性定时任务**（create_trigger，用 run_once_at，每次触发是一个新会话，所以 prompt 必须自包含）。不要用 send_later（它绑定当前会话，几周后该会话可能已不存在）。

**时间**（均为新加坡时间 09:00，换算成 UTC 即 01:00Z）：
- 写预期提醒：事件开始前2天。事件在48小时内则不设，当场问。
- 补结果提醒：事件结束后的第一个新加坡时间早上。美国时间的事件要考虑时差（如美东12月15日结束的会议 → 新加坡12月17日早上）。

**设置**：
- name：`写预期提醒：<事件简称>` / `补结果提醒：<事件简称>`
- notifications：`{"push": true}`（只推送，不发邮件）
- initiation：用户要求添加事件时为 human_request

**prompt 内容要求**（自包含，中文）：
- 开头说明这是哪类提醒，并要求使用 plan-event-tracker 技能
- 事件名称、日期、Notion 页面URL、数据库 collection ID
- 两类提醒的第一步都是 fetch 事件页面：如果状态已是"已放弃"（事件已取消）或所属主题已结案/放弃且没有改挂，就静默结束，不打扰用户
- 写预期提醒的步骤：确认没有改期 → 预期已写就只推送一句确认 → 否则读取所属主题的假设和信号、同主题先前事件的结果，并搜索最新前瞻，整理成3–5行背景 → 用 SendUserMessage 请用户回复预期（不替用户写）→ PushNotification → 用户回复后按"写预期"规则写入
- 补结果提醒的步骤：已完成就只推送一句确认 → 否则搜索核实实际结果（附来源），对照预期和主题信号 → SendUserMessage 请用户确认 → 确认后按"补结果"规则写入 → PushNotification。不要修改主题本身。用户没有回复也没关系——事件会停在"待发生"，下次复盘会把它列为漏补结果。
- 如果事件是主题的关键检验点（如主题内最后一个事件、到期日），补结果提醒里加一句：提醒用户在下次复盘时考虑结案（判定假设证实/部分成立/推翻）。

**记录**：创建后，在事件页面正文末尾追加：

```
## 提醒
- 写预期：YYYY-MM-DD 09:00（新加坡）｜trig_xxx
- 补结果：YYYY-MM-DD 09:00（新加坡）｜trig_xxx
```

## 注意事项

- 不要批量导入整份经济日历。只录入与进行中主题相关的事件；用户要求批量导入时，提醒这一原则并请他确认范围——每个事件都会带来两个提醒。
- 回复保持简短：一两句说明做了什么（含提醒时间），附页面链接。
